측정 기반: NVIDIA-NeMo/RL PR #3243 (rollout-only eval mode) + Gym PR #1825 / nv-OpenHands PR #19 (rollout timeline profiler). 스택: Lyris GB200 1n4g, vLLM 0.25.1, Qwen3-30B-A3B-Thinking-2507, Gym latest main(fbde772), nv-OpenHands sdd/multilingual-fixes@5f018005. 워크로드: SWE1-pivot 400 rollouts / SWE2(OpenHands agentic) SWE-bench_Verified 3 instances × ≤8 turns.

요약. 실측으로 확인된 비효율은 8개이며 크게 세 계열이다: (1) GPU 시간 낭비 — prefix cache가 두 워크로드 모두에서 0% 히트 (라우팅/제출 패턴 문제, I1·I2), (2) CPU측 고정비 — agent init 24.5% + framework overhead 17.2% (콜드 임포트, 순차 셋업 명령, lustre 이벤트 쓰기, I3–I5), (3) 파이프라인 직렬성 — eval이 크리티컬 패스에 있고 venv 재빌드가 반복 실험을 지배 (I7·I8). 2. 비효율 인벤토리 — 증거 / 코드 / 수정 / 트레이드오프

I1. 멀티턴 prefix cache 0% — 세션리스 클라이언트 × per-request round-robin

GPU증거: SWE2 18턴 전부 cache_read_tokens=0. 턴 프롬프트는 5.7K→16.2K→16.9K…로 성장(동일 대화 prefix)하며 매 턴 전체 재-prefill. 인스턴스당 프롬프트 토큰 합계 78K/56K/154K vs 완성 16.5K/7.6K/17.3K.

코드 (Gym responses_api_models/vllm_model/app.py:525): 어댑터는 세션-sticky 라우팅을 구현했지만, 스티키의 키가 HTTP 세션 쿠키다. 컨테이너 안 OpenHands LLM 클라이언트는 쿠키를 유지하지 않으므로 매 요청이 새 세션 → len(map) % len(clients)가 요청마다 증가 → 엄격한 엔진 교대 → 직전 턴의 KV가 항상 반대편 엔진에 있음 → 0% 히트.

수정: 스티키 키를 쿠키가 아니라 요청 내용에서 유도 — 대화 첫 user 메시지(또는 metadata.instance_id)의 해시로 클라이언트 선택. 클라이언트 수정 불필요, 어댑터 ~10줄.

기대 이득: 턴2+ prefill의 80–90% 캐시화 → SWE2 LLM 시간 −15~25%. SWE1의 same-prompt 4-gen에도 동일 적용(I2와 결합).

트레이드오프/정합성: 낮음 — (a) 부하 불균형: 긴 대화가 한 엔진에 몰릴 수 있음 → 해시 분산으로 평균은 균형, 최악 케이스는 엔진 수 늘리면 완화. (b) correctness: 없음 — 모든 엔진은 동일 가중치이며 RL refit도 전 엔진 동기 갱신; 라우팅은 어떤 엔진이 계산하느냐만 바꿈. (c) KV 캐시 메모리 압박이 특정 엔진에 몰릴 수 있으나 APC는 LRU 축출이라 안전(성능만 영향).

I2. SWE1 same-prompt 4-gen 동시 제출 → cascade miss

GPU증거: SWE1 400 rollouts 전부 cached_tokens=0 (평균 24K 토큰 프롬프트 ×4벌 = 중복 75%). 3중 검증: usage 0 ×400 / 배치 dispatch spread 61–91s가 무중복 prefill 처리량과 일치 / KV 점유 27%가 무공유 footprint와 일치.

원인: 동일 프롬프트 4개가 같은 스케줄링 웨이브에 동시 admission → APC prefix 매칭은 admission 시점에 일어나므로 아무 것도 캐시에 없음 + 엔진 분산.

수정: NeMo-RL 제출 경로에서 (a) same-prompt gens를 같은 엔진으로(I1의 해시 라우팅으로 해결) + (b) 첫 gen의 prefill 완료 후 형제 3개 제출(stagger).

기대 이득: prefill 토큰 9.67M 중 최대 75% 제거 → 배치 wall ~1.8× 추정. 학습 config(gens/prompt 8–32)에서는 중복률 87–97%라 더 큼.

트레이드오프: 낮음~중간 — (a) stagger는 형제 gen들의 시작을 첫 prefill만큼(수 초) 지연 → 배치 초반 병렬성 소폭 감소, 순 이득은 큼. (b) 구현 위치가 NeMo-RL rollout 제출 루프라 async GRPO의 in-flight 로직과의 상호작용 검증 필요(제출 순서만 바꾸므로 수학적 결과 불변 — temp 샘플링 RNG 경로는 요청별 시드라 영향 없음).

I3. connect_to_runtime = 14.84s 상수 (action server 콜드 스타트)

CPU증거: 9회 이상 측정에서 14.83–14.87s로 사실상 상수. 폴링은 2s 간격이므로 낭비 ≤2s — 지배 요인은 lustre에 마운트된 OpenHands venv에서 action_execution_server의 python 임포트 ~13s.

코드 (nv-OpenHands openhands/runtime/impl/local/local_runtime.py:415):

기대 이득: 14.8→4–6s (rollout당 −10s).

트레이드오프: 낮음 — /tmp 디스크 ~1–2GB(컨테이너 tmpfs 여유 확인됨), 복사 비용은 노드당 1회로 상각, 복사본은 잡 시작 시점 스냅샷이라 잡 도중 코드 수정이 반영 안 됨(오히려 재현성엔 이점). correctness 영향 없음.

I4. initialize_runtime = 20.6s (순차 셋업 명령 ~7개)

CPU증거: entry 스크립트 자체는 1.77s(수동 실측)인데 initialize 단계는 20.6s. run_infer.py:1016–1147이 CmdRunAction을 순차로 ~7회 실행(initial setup, entry source, 복합 명령 3, cd, git reset) — 각각 HTTP+tmux+PS1 감지 왕복(~1–2s)을 지불.

수정: 독립 셋업 명령을 1–2개 복합 명령으로 병합(cmd1 && echo M1 && cmd2 && echo M2 … 마커 방식으로 단계 식별 유지).

기대 이득: 20.6→~10s (rollout당 −10s).

트레이드오프: 낮음 — (a) 단계별 assert_and_raise의 오류 귀속 정밀도 하락 → echo 마커+rc 체크로 보완, (b) 단일 명령 타임아웃이 합산 시간을 커버해야 함(command_exec_timeout 상향), (c) 셸 상태(cd, env)는 같은 세션이라 동일. eval 정확도 영향 없음.

I5. 이벤트 스토어가 lustre에 per-event 쓰기

CPU증거: framework overhead 4.1s/턴의 구성 요소. OpenHands 이벤트 스트림(.eval_sessions)이 lustre 바인드 밑에 있어 액션/관찰 이벤트마다 lustre 파일 쓰기 발생.

코드: run_infer.py:654 — EVAL_FILE_STORE_PATH 환경변수로 오버라이드 가능 (코드 수정 자체가 불필요).

수정: 컨테이너 내 /tmp로 지정 (agent 스크립트 env 1줄).

기대 이득: 턴당 −0.5~1s (측정 후 확정).

트레이드오프: 낮음 — 이벤트 스트림 파일이 컨테이너 종료와 함께 소멸 → 디버깅용 이벤트 히스토리 상실. 단, 분석에 쓰는 trajectory(output.jsonl)와 profiler 메트릭은 별도 경로(lustre)에 보존되므로 실사용 손실 없음. resume 기능은 eval 모드에서 미사용.

I6. LLM 호출 2-hop + 매 턴 전체 히스토리 재직렬화

CPU증거: OpenHands → vllm_model 어댑터 → NeMo-RL vLLM 서버의 2-hop HTTP. 턴 N 프롬프트 = 전체 히스토리(최대 154K tok/rollout 누적) → 턴마다 300–600KB JSON 인코드/디코드 ×2 hop.

수정(중기): 어댑터 keep-alive 확인 + 어댑터측 대화 캐시(콘텐츠 해시 키)로 델타 전송.

트레이드오프: 중간 — 어댑터가 상태를 가지게 됨(메모리 성장 → LRU 축출 필요), 캐시 키 충돌/히스토리 편집(condenser 활성 시) 시 정합성 버그 가능 → 무효화 규칙 필수. 이득 대비 복잡도가 높아 I1–I5 이후로 후순위 권장.

I7. venv 재빌드가 잡마다 12–15분 (NRL_FORCE_REBUILD_VENVS=true)

DX증거: 모든 스모크 잡의 elapsed ~27분 중 rollout은 ~5분 — 셋업이 지배.

Persistent venv의 오버헤드/리스크 (질문 주신 부분):

리스크내용완화
스테일 코드lock/pyproject/휠 패치 변경이 기존 venv에 반영 안 됨 → 조용히 옛 의존성으로 실행 (이 클래스의 버그를 과거 실측으로 겪음: 컨테이너 py버전 바뀐 뒤 venv 재사용 → ModuleNotFoundError, uv lock 해시 스테일)venv 디렉토리명 = hash(uv.lock)로 자동 무효화
공유 FS 쓰기 경합동시 잡이 같은 lustre venv에 쓰면 반쯤 설치된 상태 관측 (과거 실측: 병렬 잡 ray import 실패)노드 로컬 /tmp에 두거나, lustre면 lockdir + 완료 마커
노드 이동/tmp venv는 다른 노드에서 재사용 불가lustre 스냅샷 → 노드 로컬 rsync (1회 ~30s)

권장: 반복 측정(스모크) = hash-키 persistent venv, 프로덕션/최종 수치 = FORCE_REBUILD 유지. 이 구분이면 correctness 리스크 없이 iteration 2×.

I8. Final eval이 크리티컬 패스에 직렬 (11.2%)

Pipeline수정: 채점(별도 apptainer)을 rollout 수집과 오버랩 — eval 큐 비동기화.

트레이드오프: 중간 — 벤치마크/eval 모드에서는 순수 이득이지만, RL 학습에서는 reward가 advantage 계산의 선행 조건이라 비동기 eval은 reward 도착을 늦춤 → async GRPO의 trajectory age와 상호작용(늦은 reward = 더 오래된 정책의 샘플 사용). 학습 정확성 자체는 불변이나 on-policy성이 미세하게 약화 → max_trajectory_age 예산 안에서만 적용해야 함.

3. SpecDec: LLM Generation 45.7%는 실제로 줄어드나

SWE1(prefill 22:1)에서는 안 줄었다 — 실측 0.87× (투기 대상인 decode 자체가 4.4%뿐). SWE2는 decode-heavy라 Amdahl 상한 1.21×를 기대했으나, 실측 결과 SWE2에서도 줄지 않았다:

LLM 시간 합완성 토큰tok/s턴당 p50/p90gen 배율
baseline (smoke10)198.4s41,3782096.6 / 28.41.00×
eagle3-K3 (2429766)282.8s53,4331899.4 / 25.60.90×

temp 1.0이라 trajectory가 달라져(turns 21 vs 18, 토큰 +29%) 총시간 비교는 무의미 — per-token 처리량(tok/s)이 1차 지표.

해석 — 왜 decode-heavy인데도 지는가: 두 요인의 결합. (a) I1과의 커플링: cache 0% 때문에 매 턴의 model_call_time에 6–25K 토큰 히스토리 재-prefill이 포함되고, 이 prefill은 SpecDec이 가속 못 함 — 즉 I1(sticky 라우팅) 픽스가 SpecDec 유효성의 선행 조건. (b) 장문 컨텍스트 acceptance 붕괴: EAGLE3 drafter는 6–25K 컨텍스트에서 분포 밖 — standalone에서 측정한 acceptance 급감(깊은 위치 <0.06)과 일치. 같은 스택·같은 drafter가 짧은 컨텍스트 math GRPO에서 1.63×를 내는 것과 대비. 따라서 순서는: I1 픽스 → decode 비중 회복 → SpecDec 재평가(그때도 장문 acceptance가 남는 한계면 length-aware/drafter 장문 재학습 트랙).
