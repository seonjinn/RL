One structural fix produced all of the gain: stop importing Python from Lustre. A second hypothesized fix (skipping git reset) turned out to be chasing a mis-attributed cost — a genuinely useful null result that redirected the roadmap (§4).

2. Why this matters now: the drafter moved the bottleneck

After deploying our DFlash speculative-decoding drafter at its optimal draft length (K=5), LLM generation got 1.5× faster — and the fixed costs around it became the binding constraint:

This is Amdahl's law in action: every further generation speedup is worth less until the serial overhead around it is removed. Note the flip side measured earlier: between turns the framework adds nearly nothing (98–99% of the agent call span is LLM time) — the entire overhead is a once-per-rollout cold start.

3. Inefficiency #1: Python cold-starts from Lustre (fixed)

What was happening

The OpenHands agent harness lives in a 5.3 GB directory on Lustre (swe_openhands_setup/ = OpenHands checkout + its poetry venv + a miniforge Python). Every rollout starts two fresh Python processes from it:

per rollout: [1] run_infer.py (evaluation harness) ~19 s before first useful line [2] action_execution_server (sandbox tool server) 14.8 s inside connect_to_runtime wait both interpreters resolve thousands of small files: .pth files -> site-packages -> package __init__ chains -> stdlib each open()/stat() = one Lustre metadata RPC to the MDS server

Why it is slow: Lustre is engineered for large streaming I/O, not for "stat and read 8,000 tiny .py files". Every import touches the metadata server over the network; page-cache helps little because each rollout is a new process tree and much of the cost is metadata round-trips, not data. On a local NVMe disk the same import chain takes 2–4 s.

The fix: node-local mirror with container-aware path rewriting

Once per job, copy the whole setup to node-local storage and point everything at the copy (NRL_OH_NODE_LOCAL=1, implemented in Gym's swe_agents/app.py):

# app.py :: _node_local_mirror(), called from setup()
local_root = /tmp/oh_setup_local_$SLURM_JOB_ID       # node-local NVMe
cp -a swe_openhands_setup/{OpenHands,miniforge3}  local_root/
# 1) rewrite absolute paths in text files: pyvenv.cfg, bin/* shebangs,
#    site-packages *.pth, direct_url.json, RECORD
# 2) re-point absolute symlinks (.venv/bin/python -> miniforge3/bin/python3.12)
# target prefix for BOTH rewrites: /openhands_setup   (see below, not /tmp!)
The subtle part (and how the first attempt failed): rollouts run inside an Apptainer container that bind-mounts the setup at /openhands_setup. The container cannot see the host's /tmp path. Our first attempt rewrote paths to the host /tmp/... prefix; inside the container poetry declared the venv "broken" and tried to recreate it on a read-only mount ([Errno 30] Read-only file system). The correct rewrite target is the container-side mount point /openhands_setup — the host-side bind source switches to the local mirror, and every in-container path stays valid.
HOST CONTAINER before: /lustre/.../swe_openhands_setup --bind--> /openhands_setup (imports traverse Lustre) after: /tmp/oh_setup_local_<job> --bind--> /openhands_setup (imports hit local NVMe) paths inside venv all say "/openhands_setup/..." -- valid only in-container, by design

Why this is safe

  • The setup is read-only at runtime and byte-identical for every rollout — mirroring changes where it is read from, not what is read.
  • Guarded by an env flag, default off; zero impact on existing runs.
  • Correctness A/B: same benchmark, same drafter — 316 tok/s and sane scores after the patch.

Cost model: when the mirror pays for itself

Measured216 s~16 s≈ 14 rollouts

Planned upgrade — squashfs bake: the mirror content is identical across nodes and jobs, so copying it repeatedly is still wasteful. Building it once into a squashfs image and bind-mounting it read-only turns "thousands of small-file RPCs" into "one big cached file": per-job cost drops from 216 s to ~0, staleness is handled by versioned image names. Lustre is bad at many small files, but perfectly fast at one 5 GB file.

4. Inefficiency #2: the git myth (a useful null result)

Instrumentation showed initialize_runtime = 20.1 s per rollout, and the visible command in that window is source entry_script && cd workspace && git reset --hard. We attributed the cost to git churning the repository and added an opt-in skip (NRL_SKIP_GIT_RESET=1 — safe because the workspace is freshly copied from the image and therefore already clean).

Result: the skip works (zero git reset executions in the logs) and saves nothing (20.1 → 19.9 s).

What the null result taught us: the ~20 s is the workspace copy performed by the entry script — extracting the instance repository out of the compressed squashfs container image into /workspace. Git was never the problem. This redirects the next fix: cache the extracted repository per instance on node-local disk (first rollout of an instance pays the extraction, all re-rollouts reuse it). That pattern fits RL training exactly, because GRPO re-rolls the same instance pool every step.

5. What was already fine (checked, not fixed)

  • Inter-turn framework overhead ≈ 0. Between agent turns, 98–99% of the call span is LLM time. No per-turn tax to remove.
  • Apptainer container spin-up ≈ 0.7 s. SIF caching works.
  • Two earlier micro-patches (retry interval 2s→0.5s, merged-init round-trip fusion, file-store relocation) measured ≈ zero gain in an honest A/B — the mass was never in those places.
