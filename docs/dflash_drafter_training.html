Everything that goes into our speculative-decoding drafters: the datasets (with train/test separation guarantees), the software stack, the training configuration, and the wall-clock relay that fits multi-day training into 4-hour queue slots. Train/test separation (three walls, all enforced in code): (1) instance wall — evaluation = 3 astropy SWE-bench_Verified instances (12907/13236/13398); the training pool = 7 disjoint instances (django×4, sympy, sphinx, requests); (2) content wall — any public-SWE conversation that even mentions "astropy" is dropped (827 dropped); (3) fingerprint gate — the final 850K corpus is scanned for the eval instance IDs, distinctive problem-statement phrases, and the OpenHands system prompt before training may start (result: 0 hits). The gate is not theoretical: it caught a real contamination accident (a dataset-builder bug had stamped astropy's task payload into 1,680 pool rows) and blocked it from entering training.

3. Software stack

AWS-DFW GB200 (aarch64), 2 nodes per training job ┌────────────────────────────────────┐ ┌──────────────────────────────────────┐ │ Node 0 — target server │ │ Node 1 — drafter training │ │ vLLM 0.25.x (vllm_venv, uv py3.12) │ │ speculators @ repo HEAD (editable) │ │ Qwen3-235B-A22B-Thinking, TP=4 │──▶│ + hs_connectors sub-package │ │ --target-layer-ids 1 23 46 68 91 │ │ torchrun --nproc_per_node 4 │ │ hidden-state KV-connector ────────▶│ │ FileBackend reads from lustre cache │ │ --hidden-states-path (lustre) │ │ --vllm-endpoint http://node0:8000/v1 │ └────────────────────────────────────┘ └──────────────────────────────────────┘
  • Trainer: vllm-project/speculators installed editable from the repo (scripts/train.py + scripts/prepare_data.py); the PyPI release lags the repo scripts.
  • Online mode (--on-missing generate --on-generate delete): the target regenerates every response and streams hidden states through a shared-filesystem connector; nothing is stored (offline caching would have needed 24–40 TB for this corpus).
  • Cross-node: training connects to the server via --vllm-endpoint; hidden-state files transit a lustre path visible to both nodes.
  • Cluster plumbing: CUDA_HOME=/cm/shared/apps/cuda13.0/toolkit/13.0.2 + ninja/cmake in the venv (GB200 sm_100 JIT), TMPDIR=/tmp (ZMQ 107-char limit), system-forced HF_HUB_CACHE on the project share.
  • Drafter checkpoints are speculators-format (DFlashDraftModel) — loaded directly by vLLM 0.25 speculative_config with no conversion; shipped between clusters via PBSS S3 (~1 min for 4 GB).

4.1 The wall-clock relay (how 26+ hours fit in 4-hour queue slots)

sbatch chain (interactive QoS, starts in seconds; batch_long queue waits hours): c1 ──afterany──▶ c2 ──▶ c3 ──▶ … ──▶ c8 ──afterany──▶ batch_long finisher (40h) each chunk: same sbatch, same --save-path → trainer auto-resumes (epoch + mid-epoch step skip from training_state.json; optimizer/scheduler restored) finished early? remaining chunks boot, see "nothing to train", exit in minutes (idempotent)

Chunks are wall-time, not data: the total sample count is fixed by (unique samples × epochs) — v2 trains 1,700,440 passes whether it takes 5 chunks or 8.

5. Evaluation methodology

  • During training: per-epoch validation reports EAL (expected acceptance length = Σk P(first k draft tokens all accepted)) and per-position acceptance. Useful for screening, but only comparable within one val distribution — we measured a drafter with val EAL 3.27 (100% SWE-smith) that was slower on real rollouts than one at 1.86.
  • The real scoreboard: NemoGym SWE2 rollouts (OpenHands agent, apptainer per instance, vLLM 0.25, K=5) on the held-out astropy instances — tok/s = completion tokens ÷ model-call time.
  • Contamination scans accompany every claim: v1's 1.33× was backed by scanning all 628,540 training rows for eval fingerprints (0 hits).
