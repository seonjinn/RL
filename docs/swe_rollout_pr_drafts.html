[SWE] Stage the OpenHands runtime on node-local storage

Repository: NVIDIA-NeMo/Gym

Root cause: every rollout starts a new OpenHands process and action server. Importing thousands of OpenHands and miniforge files from shared storage makes Connect and Framework startup slow.

Summary

Stage OpenHands and miniforge on node-local storage once per job. SWE rollout containers mount the staged copy at the existing /openhands_setup path.

High-level implementation

  • Add an opt-in node-local staging mode to swe_agents/app.py.
  • Build an immutable runtime contract and populate a job-scoped cache under a lock.
  • Rewrite only known environment metadata and shebang launchers for /openhands_setup.
  • Verify source stability, publish an atomic manifest, and keep shared storage as the fallback.

Performance impact

  • Measured Connect: 15.0 to 11.1 s per rollout, 26.0% lower.
  • Measured Framework: 21.8 to 16.4 s per rollout, 24.8% lower.
  • Measured Combined saving: 9.3 s/rollout; generation stayed at 276-277 tok/s.
  • Pending measurement Refreshed latest-main setup-inclusive allocation-to-result A/B.

Validation before ready-for-review

  • Run matched n=24 baseline versus node-local jobs, including the 216 s first-copy cost, failures, and drain.
  • Require reward, valid-rate, generated-patch, and generation-throughput parity.
  • Run n=80 only if n=24 is inconclusive but per-rollout Connect + Framework savings remain at least 5 s.

[SWE] Harden OpenHands startup phase metrics

Repository: seonjinn/nv-OpenHands, targeting the SWE branch

Root cause: startup timers exist, but metrics output must remain optional and safe for standalone runs, partial failures, and concurrent readers.

Summary

Move startup metric updates into a small tested helper. Treat a missing metrics path as disabled and publish JSON updates atomically without changing rollout behavior.

High-level implementation

  • Keep the existing monotonic phase names and numeric values.
  • Handle missing, empty, malformed, and valid metrics files explicitly.
  • Write to a temporary sibling and use atomic replace.
  • Do not change OpenHands commands, retries, or environment lifecycle.

Performance impact

No intended speedup. Accept only if median overhead is at most 0.5% and p95 overhead is at most 1%.

Validation before draft

Focused helper tests, standalone and Gym output parity, non-negative phase fields, and enabled-versus-disabled overhead comparison.

[SWE] Support an immutable workspace cache

Repository: seonjinn/nv-OpenHands, targeting the SWE branch

Root cause: cp -al crosses the read-only testbed and writable workspace filesystems, fails, and falls back to a full cp -r for every rollout.

Summary

Allow the SWE entry script to build a private writable workspace from an optional read-only, immutable cache.

High-level implementation

  • Validate instance ID, source image identity, and base commit.
  • Use a private reflink clone when supported; evaluate a private OverlayFS path separately.
  • Fall back to the current full copy when the cache is missing, stale, or unsupported.
  • Never expose shared writable inodes to multiple rollouts.

Performance target

Projected Warm Initialize: 21.8 to at most 5 s, saving at least 16.8 s per rollout.

Promotion gate

Two concurrent rollouts must prove no file leakage; base commit, patch, trajectory, and reward must match the current path. Cache miss, stale cache, unsupported reflink, and interrupted population must fall back safely.

[SWE] Stage and mount immutable workspace caches

Repository: NVIDIA-NeMo/Gym

Dependency: the nv-OpenHands immutable workspace-cache consumer contract above.

Summary

Make Gym the safe owner of an immutable per-instance template and mount it read-only at the private OpenHands cache path.

High-level implementation

  • Key the cache by source image identity, instance ID, and base commit.
  • Populate under a lock in a temporary directory and publish with atomic rename.
  • Verify a manifest before every mount.
  • Keep /workspace private and writable for each rollout.

Performance target

  • Projected Warm Initialize at most 5 s.
  • Projected At least 8% lower n=80 allocation-to-result wall.
  • Do not count the consumer and producer benefit twice.

Promotion gate

Cold- and warm-cache tests; locking, atomic publication, manifest rejection, safe fallback, identical patches and rewards, and no new failure class.

Progressive optimization queue

Test one mechanism at a time. Promote a candidate only when its named phase improves and its correctness gate passes.

Priority and candidateTargeted root causeQuantitative acceptance gateRisk and stop condition
1. Prebuilt runtime artifact
Projected		 Replace the 5.3 GB, 216 s per-job recursive mirror with a baked container layer or versioned squashfs mount. Setup at most 36 s and at least 180 s below the current copy; byte-level manifest parity; no valid-rate or rollout-phase regression. Low implementation risk. Stop if image distribution or mount cost consumes the saved setup time.
2. Private CoW workspace
Projected		 Eliminate the cross-filesystem cp -al failure and full cp -r fallback. Warm Initialize at most 5 s; n=80 job wall at least 8% lower; identical base commit, patch, reward, and trajectory; zero cross-rollout file leakage. Filesystem support and isolation are the primary risks. Stop on any shared writable inode or unsupported fallback ambiguity.
3. Pre-imported forkserver
Projected		 Pay the one-shot run_infer.py import cost once while retaining a fresh child per rollout. Framework at least 3 s lower and allocation-to-result wall at least 2% lower; deterministic event ordering and output parity. Fork only before CUDA, threads, sockets, and loggers are initialized. Stop on inherited process state or nondeterministic shutdown.
4. One-use prewarmed action servers
Projected		 Move action-server import and /alive boot off the rollout critical path without reusing a dirty server. Connect p50 at most 5 s and p95 at least 30% lower; every server receives exactly one lease and is destroyed afterward. Stop on process, environment, filesystem, secret, tmux, plugin, todo, or download state leakage.
5. Trajectory payload compaction
Projected		 After #3390, avoid persisting duplicate token/logprob representations while preserving the OpenAI response contract. Serialized trajectory bytes at least 10% lower and serialization CPU p50 at least 5% lower; token IDs, selected logprobs, rewards, and replay behavior identical. Stop if any public response field changes or offline replay loses information.
6. nv-OpenHands episode affinity
Projected		 Keep consecutive turns of one episode on the same vLLM replica so eligible KV prefixes are local. Eligible prefix-cache hit rate at least 30% and long-context prefill wall at least 5% lower; no more than 2% generation-throughput regression. Use conversation or instance identity, never mutable global order. Stop on load imbalance or session cross-talk.
Do not add percentages across unmatched experiments. #3390 targets the per-turn model-serving critical path, #3283 targets Ray actor dispatch, and local startup changes target Connect, Initialize, or Framework. Combined impact must come from a matched multi-arm run.

Validation and promotion workflow

Static + unit→ n=1 correctness→ n=24 matched A/B→ Conditional n=80→ Promote or drop
GateRequired evidence
CorrectnessSame base commit and inputs; generated-patch, reward, trajectory, valid-rate, and fallback parity.
IsolationNo workspace, process, environment, credential, server, or cache state crosses rollout boundaries.
PerformanceAllocation-to-result job wall includes setup, failures, and drain. Report phase sums and summed concurrent rollout durations separately.
Operational safetyNo new timeout, OOM, Ray, stale-cache, workspace-isolation, or process-leak failure class.
PromotionOnly measured, reproducible effects enter a ready-for-review PR. Null or unsafe candidates remain in the attempt ledger and are dropped.
