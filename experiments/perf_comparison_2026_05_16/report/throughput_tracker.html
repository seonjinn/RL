divisible by weight quantization block_n = 128.
  File ".../vllm/model_executor/layers/quantization/fp8.py", line 767,

Root cause: Qwen3-235B-A22B-Thinking-2507-FP8 has MoE intermediate_size=1536. With vllm_cfg.tensor_parallel_size=8, each shard gets 1536/8 = 192. vllm's blockwise FP8 path requires output_size % block_n == 0, but 192 % 128 = 64 ≠ 0. Raised inside upstream vllm fp8.py:767 create_weights, identical across all 7 worker ranks.

This is NOT:

  • An environmental failure (worktree submodules were initialized this run; SETUP passed).
  • A PR #2037 port bug (the failing path is upstream vllm blockwise FP8 quant, called for any FP8 model with weight_block_size=[128,128]).
  • A vllm version regression (same logic present in vllm 0.13 and 0.17).

Two mitigation paths, neither attempted:

  1. Drop TP from 8 → 4 for vllm rollout: 1536/4 = 384 = 128×3 ✓. But TP=4 doubles per-shard weights → memory pressure on 80 GB H100, possible OOM. Generation topology shifts (currently 8nodes × 8 GPU at TP=8; TP=4 means 16 vllm instances at 4 GPU each). Async GRPO traffic patterns change. Validate first with vllm-only smoke.
  2. Skip FP8 on MoE layers via ignored_layers or per-layer quant overrides. But the bulk of the refit gain was on MoE weights specifically — this loses most of the expected win.

Recognition signature: driver exit 1:0 at ~14-15 min elapsed (after env build + worker injection but before model load completes). Grep ray-driver.log for output_size.*not divisible by weight quantization block_n.

Memory feedback_fp8_blockwise_192_not_div_128 captured. Practical optimization-stack answer for H100 remains HybridEP-only.
