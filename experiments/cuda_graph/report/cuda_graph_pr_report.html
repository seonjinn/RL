1. What this work adds

Goal: enable partial CUDA graphs (TE make_graphed_callables via Megatron's TECudaGraphHelper) for GRPO policy training in NeMo-RL while sequence packing (THD format) is active, measure the speedup on policy training and logprob phases, and verify there is no accuracy impact.

  • Megatron-LM (fork branch sj/cudagraph-on-ultra): static GPU buffers for PackedSeqParams; capture with a dummy PSP; replay-time copy_() of real cu_seqlens into shared per-layer buffers; new configs cuda_graph_packed_seq / cuda_graph_max_packed_seqs; eager fallback when a batch exceeds the bucket; scope selection attn / mlp / moe / moe_router / mamba.
  • NeMo-RL: config plumbing (cuda_graph_* in MegatronConfig), bucket padding in data.py (cuda_graph_buckets, min-fill fallback), lazy capture in megatron_policy_worker.py (warmup → capture at gb0 → replay), .item()-storm elimination, offload copy-stream work, 31 CG/noCG recipes.

2. What was wrong — the critical finding

Packed batches were replayed through attention graphs captured without packed-seq support. The former "Qwen safeguard" (sequence_packing=true + cuda_graph_packed_seq=false while the CG scope includes attn) captured the sbhd attention path, then silently dropped PackedSeqParams at replay (dataclass filtered from graph kwargs). Attention ran causally over the whole packed 4096-token stream — documents were not isolated from each other, so training numerics differ from the no-CG baseline by construction.

Impact on previous results: the Apr-30 Qwen3-8B packed attn / attn+mlp CG numbers (up to “+105% policy training”) were measured in this mode and are invalid as evidence for the packed path. Unpacked (nopack) numbers and mlp-only-scope numbers are unaffected (attention runs eagerly with the real PSP in mlp scope). Rewards stayed in-noise over 20 steps because rollouts/logprob run eagerly, which is why this went unnoticed.

Fix: setup.py now enforces cuda_graph_packed_seq=true whenever packing is on and the scope includes attention, and Megatron raises instead of silently dropping a PSP into a non-packed graph.

Why the Llama/Qwen asymmetry? CUDA-graph net gain per scope = (launch/framework overhead removed from that region) − (fixed costs: per-layer graph entry + static input copies + flash→cuDNN FusedAttention substitution). Llama's attention region is already launch-lean in eager mode (one RMSNorm + QKV/O GEMMs + a single FlashAttention kernel), so there is little overhead to recover and the fixed costs dominate → net loss. Qwen3's attention region is structurally heavier (per-layer QK-Norm adds extra small kernels; 36 vs 32 layers), and its eager baseline is correspondingly slower (nopack train 109.6 s vs Llama 87.0 s at the same scale) — that surplus is exactly the launch overhead CUDA graphs eliminate, so attention capture pays off. Mask copies were ruled out by the mask-elimination A/B and the backend was verified as FusedAttention in both regimes. A forced-FlashAttention experiment (2026-07-16, job 5430256, attention_backend=flash, 87 confirmed flash selections under capture) settled the kernel-substitution hypothesis: with FlashAttention inside the graph, Llama attn-scope policy training got slightly slower (68.7 → 74.4 s), while the eager logprob phase got faster (11.3 → 8.4 s). The attention-scope regression is therefore driven by per-layer graph fixed costs (graph entry + static input copies), not kernel choice — pointing at TE ≥ 2.7 buffer-reuse or chunk-wise (whole-block) capture as the remedies.

Reading: for Llama the win comes from graphing the MLP region (+82–88% policy-training throughput, +38% E2E). Putting attention inside the graph is counterproductive on GB200 (the CG-compatible TE attention path is slower than eager FlashAttention, and per-layer graph re-entry costs dominate); attn+mlp lands in between. Logprob and generation phases are flat across configs, as expected.

3.3 Qwen3-8B · sequence packing ON

Rows flagged below ran in the pre-fix mode (cuda_graph_packed_seq=false with attention in scope): the graphs computed cross-document attention, so their speedups are not valid evidence for the packed path. They are retained for the record. The mlp-scope rows are valid (attention runs eagerly with the real PSP). Packed attn-scope CG was re-measured on 2026-07-15 with the fixed THD capture (latest-main merge stack, job 5353054, steps 11–20): E2E 307.6 s · policy training 194.1 s · logprob 33.7 s · generation 75.1 s — i.e. ~2× slower policy training than the packed no-CG baseline, matching the original April THD-capture regression (185–203 s) and confirming the flagged rows were artifacts. Follow-up measurements (2026-07-15, job 5378155, attn-only scope + mask-copy-elimination optimization, steps 11–20: E2E 313.4 s · train 197.4 s): NVTE_DEBUG confirmed the packed CG path selects the cuDNN FusedAttention backend (not Unfused), and removing the S² mask copies does not rescue packed attention CG — the regression is intrinsic to the cuDNN-THD graph replay path plus per-layer graph fixed costs.

3.5 Accuracy

Across all 28 runs, per-run mean reward stays within noise of its baseline (Llama 0.438–0.450; Qwen 0.527–0.533), and logprob/generation phase timings are flat. Caveat: 20-step reward is a weak accuracy signal (rollout and logprob run eagerly); the flagged Qwen rows prove it cannot catch wrong training-path numerics alone. For release-grade validation, run the fixed configs 40+ steps with fixed seed and compare reward / val-accuracy / mean-logprob trajectories (tolerance < 1e-4 at step 40, per the experiment guide).

4. MoE (Qwen3-30B-A3B) — status

No valid MoE CG numbers exist yet. All 16 Qwen3-30B-A3B multi-node runs (May 1, r3–r7 + rerun; nocg / attn / moe_router / attn+moe_router) died before training: the ray.sub launcher failed with “Unable to locate Ray CLI module” — a container/venv mismatch — plus an earlier 1-task-srun launcher that only saw the head node's 4 GPUs.

2026-07-15 rerun attempts (11 submissions, all failed pre-training; each failure diagnosed): the committed ray.sub fixes (GRES-suffix parsing, Ray-CLI fallback, RAY_ADDRESS) DO bring the 4-node Ray cluster up on the 2026-06-24 container, but the driver's uv run cannot resolve dependencies on Python-3.13 containers: nvidia-resiliency-ext ships no cp313 wheel and the workspace requires the nvrx extra; the historical May lock pinned it to a git source, but that pin lived only in the lock, so any re-lock fails. Secondary blockers found and fixed along the way: lost exec bits on committed scripts, a stale 7.8 GB .venv (nemo-rl 0.5.0rc0) shadowing uv run --no-sync, and May-manifests + July-submodule being mutually incompatible (uv sync wipes the container venv, then dies building megatron-core).

Final 2026-07-15 status: after the dependency fixes landed, seven further 4-node matrix attempts all failed at vLLM actor startup (ActorUnschedulableError; raylet default workers crash-loop with ray._private.node import errors although the image venv is intact and worker venvs were pre-built via prefetch_venvs) — narrowed to a Ray multi-node worker-spawn issue on this stack, not to the CG code. A 1-node fallback (TP4 + full optimizer CPU offload) reached worker init but hit host-RAM OOM during HF import; a converted Megatron checkpoint cache (Qwen3-30B-A3B-Thinking-2507, 57 GB) was located and retried (2026-07-16, job 5393467): the cache hit eliminated the import entirely, yet host RAM was still exhausted — the ceiling is the full optimizer offload itself (~30B Adam state) plus colocated vLLM, so the 1-node path is infeasible on this node type (offload fractions below 1.0 are unsupported). April's Nemotron-3 MoE artifacts were checked and contain no usable steady-state data (≤2 steps). MoE baseline-vs-CG numbers therefore remain outstanding; resume assets: the checkpoint-cache 1-node path, or the captured raylet/worker session logs (job 5369107) for the multi-node root cause. Matrix definition unchanged: nocg / cg-attn / cg-moe-router / cg-attn-moe-router (w6, packed, packed_seq=true), wandb nemo-rl-cudagraph; moe full scope requires drop-padding MoE, moe_router(+preprocess) is the safe partial scope for A3B.

2026-07-16 root cause — RESOLVED (forensic log analysis + 3 diagnostic container probes, no CG code involved). The multi-node failures had two independent causes, both defects of the nemo_rl_nightly_20260711 image, and both masked on 1-node runs because the head container was repaired inline while worker containers never were:

  • Broken prebaked venvs. The image ships /opt/ray_venvs/…VllmGenerationWorker whose site-packages is a symlink farm into /root/.cache/uv/archive-v0/… (10 real files under ray/ vs 2,864 in the base env), and whose bin/python points at cpython-3.13.13 while the image only ships 3.13.11. At runtime ray.sub mounts the user's lustre uv cache over /root/.cache/uv, so whether any given module resolves depends on what happens to sit in that cache — import ray succeeded while ray._private.node did not. NeMo-RL's _env_builder/uv sync cannot catch this: uv validates installs by dist-info version only, never file integrity, so the broken tree passes as "synced" and every vLLM worker spawn dies at import (5 retries → ActorUnschedulableError).
  • Broken baked transformers in the base env. MathEnvironment runs with PY_EXECUTABLES.SYSTEM on any node; worker-node containers still had the image's corrupt transformers (transformers.tokenization_utils_base missing) because the reinstall repair ran only in the head container's driver command.
  • Why the venv override never took. The launcher exported NEMO_RL_VENV_DIR at sbatch time, but enroot resets it to the image's baked ENV (/opt/ray_venvs), so prefetch_venvs "successfully" validated the broken prebakes instead of building clean ones.

Fix (committed locally on the mainmerge branch, b3a7a829f; pending cluster validation before push): (1) export NEMO_RL_VENV_DIR inside the driver command so prefetch builds complete venvs from our own uv.lock into a fresh lustre directory, bypassing the broken prebakes; (2) per-node base-env transformers repair in ray.sub (head + worker blocks, gated by NRL_REPAIR_TRANSFORMERS); (3) prefetch filtered to the two tiers this job uses. With these, the MoE matrix (nocg / cg-attn / cg-moe-router / cg-attn-moe-router) is expected to reach training on 4 nodes.
