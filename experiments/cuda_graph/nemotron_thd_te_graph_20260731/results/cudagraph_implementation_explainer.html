01 · 배경

무엇을 다시 재생할 수 있게 만드는가?

CUDA Graph는 안정적인 GPU 실행 경로를 한 번 기록하고 재생하여 반복되는 CPU launch 작업을 줄입니다. 대신 tensor 주소와 shape, 제어 흐름, 분산 schedule geometry가 capture 당시와 호환되어야 합니다.

  • Nano 20-step baseline, attention, attention+Mamba, attention+Mamba+router 네 run이 모두 20/20 step을 완료했습니다.
  • 세 CUDA Graph scope 모두 eligible call coverage 100%, fallback 0을 기록했습니다.
  • Logprob phase를 지나도 graph bank와 graph-owned storage를 유지하도록 lifecycle reset 문제를 수정했습니다.
  • Matched 100-step correctness soak는 OCI-HSG job 5908997(baseline)과 5909007(attention)에서 실행 중이며, 2026-08-05 21:45 PDT 기준 두 작업 모두 RUNNING입니다.
20-step smoke 동작 확인
기초 배경: CUDA Graph, partial graph, THD packing

일반적인 PyTorch eager 실행은 매 iteration마다 CPU가 많은 GPU kernel을 하나씩 launch합니다. Kernel 자체가 짧거나 module 경계가 잘게 나뉘면 이 CPU launch overhead가 GPU 계산 사이의 빈 공간으로 나타납니다.

CUDA Graph는 한 번 실행한 GPU 작업의 launch 순서와 dependency를 기록한 뒤, 이후에는 graph 하나를 replay합니다. 하지만 replay는 같은 tensor 주소와 호환되는 shape 및 control flow를 요구합니다. 입력 storage가 이동하거나 동적인 분기가 달라지면 이전 capture를 그대로 사용할 수 없습니다.

Transformer Engine partial CUDA Graph는 model 전체가 아니라 attention, MLP, Mamba, MoE router 같은 선택된 submodule만 graph로 감쌉니다. Sequence packing이나 RL phase 전환처럼 동적인 바깥 부분은 eager로 유지하면서 반복적인 model 계산의 launch overhead만 줄이는 방식입니다.

THD format은 여러 가변 길이 sequence의 token을 한 줄로 이어 붙이고 cu_seqlens로 경계를 표현합니다. Token 수와 sequence 수가 매 batch마다 달라질 수 있기 때문에, graph replay를 위해서는 token capacity뿐 아니라 cu_seqlens entry 수와 관련 metadata에도 고정된 upper bound가 필요합니다.

구분해야 할 경계Generation에는 vLLM의 별도 CUDA Graph가 있습니다. 이 페이지에서 다루는 것은 Megatron policy-training 경로의 Transformer Engine partial graph입니다. Logprob 시간이 빨라졌다는 사실만으로 logprob 자체가 TE graph를 replay했다고 결론 내릴 수 없습니다.

NeMo-RL은 rollout generation, policy/reference logprob, policy training, weight refit을 하나의 RL step에서 번갈아 실행합니다. TE partial graph는 현재 policy-training 경로에서 직접 capture되며, phase 전환 중 model·gradient storage 주소가 유지되어야 다음 training call에서 같은 bank를 재사용할 수 있습니다.

Packed batch마다 실제 logical token 수는 달라도 physical storage는 token capacity와 thd_max_packed_sequences에 맞춰 padding합니다. 첫 실제 microbatch의 PackedSeqParams를 capture 입력으로 사용하고, 모든 model-parallel rank가 schedule key와 geometry에 동의한 뒤 capture를 시작합니다.

Schedule별 graph bank는 bounded LRU에 저장됩니다. 현재 capacity는 2입니다. Attention만 사용한 run에는 충분했지만, 더 넓은 scope에서 네 종류의 token-capacity schedule이 번갈아 나타나면 eviction과 recapture가 발생합니다.

03

Worker가 warmup, capture, hit, eviction을 하나의 lifecycle로 관리합니다

04 · 현재 문제

기능적으로 동작하는 것과 완성된 것은 다릅니다.

최신 smoke run에서는 선택한 scope들이 fatal error 없이 capture와 replay를 수행했습니다. 이제 남은 질문은 cache 효율, memory 비용, phase별 성능 귀속, convergence 수준의 correctness입니다.

확인된 문제

넓은 scope에서 capacity-2 bank가 thrash합니다

Attention은 step 11–19에서 hit rate 100%였지만 attention+Mamba는 55.6%, router까지 추가하면 33.3%로 내려갑니다. 네 token-capacity schedule이 두 bank slot을 번갈아 밀어내기 때문에 recapture 비용이 생깁니다.

다음 검증동일 workload에서 bank capacity 2와 4, deterministic capacity bucketing을 GPU memory peak와 함께 비교합니다.
Correctness 위험

20 step은 convergence correctness를 증명하지 못합니다

NaN/Inf, masked sequence, fallback은 없었지만 각 run이 독립적인 stochastic trajectory를 사용했습니다. Reward와 validation accuracy 차이를 CUDA Graph의 numerical impact라고 분리할 수 없습니다.

다음 검증현재 실행 중인 matched 100-step baseline/attention soak를 완료하고 step window와 seed, input 분포를 함께 비교합니다.
추가 측정 필요

Logprob 성능 향상의 원인을 아직 분리하지 못했습니다

현재 TE partial graph capture는 policy-training 경로에서 수행됩니다. Logprob throughput 향상은 storage 유지, cache 상태, workload 차이에서 간접적으로 올 수 있으며, phase-specific graph counter가 없으면 TE replay 효과라고 말할 수 없습니다.

다음 검증Policy training과 logprob phase를 구분하는 graph-call telemetry를 추가하거나 고정 input microbenchmark로 직접 attribution합니다.
추가 측정 필요

Bank capacity를 늘리면 memory가 함께 늘어납니다

각 schedule bank는 CUDA Graph executable과 static input/output storage를 유지합니다. Capacity 4는 eviction을 줄일 가능성이 있지만 Nano보다 큰 Super·Ultra와 MoE scope에서 OOM 위험을 키울 수 있습니다.

다음 검증Capture 전후 allocated/reserved memory와 bank별 retained bytes를 기록하고 model·scope별 안전한 capacity를 정합니다.
Correctness 위험

Mamba와 MoE는 attention보다 더 많은 runtime invariant를 가집니다

Mamba는 hybrid layer pattern과 CP metadata가 맞아야 하며, MoE router/preprocess는 token routing, auxiliary-loss ownership, dropless dispatcher metadata가 replay에서도 동일한 의미를 가져야 합니다. 100% coverage만으로 output·gradient parity가 보장되지는 않습니다.

다음 검증고정 packed input에 대해 eager 대 graph output, router top-k, expert count, aux loss, gradient, parameter delta parity gate를 scope별로 실행합니다.
추가 측정 필요

Upstream main과 nested dependency가 계속 이동합니다

현재 branch는 PR 5672 계열의 THD partial graph 수정과 이후 Megatron main 변경을 함께 포함합니다. NeMo-RL main과 nested Bridge/MCore가 갱신되면 API와 이미 merge된 수정이 겹치는지 다시 확인해야 합니다.

다음 검증Upstream merge 전에 NeMo-RL, Bridge, MCore의 exact commit과 diff provenance를 다시 고정하고 중복 patch 및 regression test를 audit합니다.
