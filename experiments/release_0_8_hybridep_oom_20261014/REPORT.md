MiniMax then failed on the first backward because the patch still allocated a 6.25 GiB dense logits gradient. ## Working hypothesis

MiniMax already has `train_micro_batch_size=1` and activation checkpointing enabled. HybridEP may raise the persistent GPU memory floor through its dispatch buffers, leaving insufficient room for AdamW's first-step foreach temporary tensors. This remains an inference: the DeepEP control stopped at its `internode_dispatch()` timeout during logprob inference, before policy training. The `foreach=false` control did not establish that the first optimizer step can finish because its first policy forward failed earlier. Its process used 67.78 GiB including non-PyTorch memory, another process used 5.71 GiB, and 5.51 GiB was free before a 6.25 GiB `torch.nn.functional.log_softmax` allocation. The HybridEP control also logged multi-node buffer reallocation warnings, but the buffer size was not measured.

The 6.25 GiB MiniMax request is a full-sequence FP32 log-softmax over a large vocabulary, not a direct HybridEP allocation. Qwen later failed at the same site on an 8.53 GiB allocation. The recipes set `policy.logprob_chunk_size` to 2,048 (MiniMax) and 4,096 (Qwen), but `LossPostProcessor` did not pass that value into `prepare_loss_input()` during policy training. The non-parallel path in `get_next_token_logprobs_from_logits()` cast full logits to FP32 and materialized full log-softmax output. The code now passes the configured chunk size into the policy loss and uses a local custom autograd function that casts and normalizes one sequence chunk at a time, saving the original logits and recomputing softmax by chunk during backward. The regression test failed against the unpatched release code in CW CPU job `20221823`. Local numerical and saved-tensor tests passed with the patch (4/4). Container CPU validation `20222621` completed with one passed test. Both full-length GPU jobs use a 512-token calculation chunk. MiniMax additionally sets `foreach=false`. They preserve policy total lengths of 10,240 and 9,216 and generation maxima of 8,192 for MiniMax and Qwen respectively. Preallocating HybridEP's larger buffer may remove its reallocation warning but should not be assumed to lower peak GPU memory.

Qwen uses Transformer Engine `FusedAdam`, so the MiniMax foreach control does not apply to its optimizer.

## Full-length patched runs and next controls

MiniMax `20222741` reached `ChunkedLocalLogprob.backward()` in the first policy step. The failed `torch.empty_like(logits)` was 6.25 GiB, with 4.78 GiB free on a 79.11 GiB H100. Policy memory was 68.50 GiB and the colocated vLLM process held 5.71 GiB. Chunking FP32 softmax bounds temporary memory, but PyTorch autograd still requires a dense BF16 gradient for the already materialized `[batch, sequence, vocabulary]` logits. Reducing `logprob_chunk_size` further cannot eliminate that allocation. The existing Automodel FSDP `policy.automodel_cfg.cpu_offload=true` moves sharded parameters and optimizer state to CPU; the next control tests whether that frees enough GPU headroom while retaining full sequence and generation lengths. A source-level solution would fuse LM-head projection with per-token logprob calculation, accumulating hidden-state and weight gradients by chunk without a dense vocabulary gradient.

The pinned Automodel MiniMax-M2 class declares `supports_tp=False` and `supports_cp=False`; its loader validates the requested mesh against these capabilities. NeMo-RL's Automodel setup also fixes pipeline parallelism at one stage. TP and EP use overlapping mesh axes in this Automodel version: TP8 plus EP64 is topologically valid on 64 GPUs. The earlier assertion that this combination needs 512 GPUs was incorrect. The remaining blocker is the model's missing TP plan, which must be checked in a live container run. Changing EP alone does not shard the LM-head vocabulary or sequence dimensions and cannot directly remove the dense logits gradient allocation. EP128 on 128 GPUs could reduce expert-state memory per rank, but would leave that gradient allocation intact and has not been tested.

Qwen `20222812` completed nine policy steps with the same chunked code, then failed during step 10 generation. A vLLM worker requested 128 MiB in `fused_add_rms_norm` with 117 MiB free; that worker held 36.11 GiB and another policy process held 42.85 GiB. Startup allocated a 21.99 GiB KV cache, while observed cache usage during generation peaked near 25%. The next control pins `policy.generation.vllm_kwargs.kv_cache_memory_bytes=17179869184` (16 GiB). At the startup-reported 1,953,100 tokens for 21.99 GiB, that still represents roughly 1.42 million token slots, above 128 concurrent full-length 9,216-token requests. This changes cache capacity, not `policy.max_total_sequence_length=9216` or `policy.generation.max_new_tokens=8192`.
