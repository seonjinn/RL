HybridEP Impact

HybridEP does not directly raise SpecDec acceptance or raw rollout Generation throughput. Its value is that it can shrink policy training and logprob time, so a fixed Generation speedup contributes more to E2E step speedup.

QuestionCurrent EvidenceImplication
Will HybridEP make SpecDec generation faster? No direct evidence. Generation is run by vLLM workers; HybridEP mainly targets MoE policy/logprob/training efficiency. Do not expect acceptance rate or generated tok/s/GPU to improve just because HybridEP is enabled.
Will HybridEP make SpecDec E2E speedup larger? Likely, if it reduces the non-generation part of the GRPO step without adding rollout/sync overhead. SpecDec gains are currently diluted because logprobs and training dominate total step time.
Observed dilution on 30B p64/g32 Steps 1-4 mean baseline 3078629: generation 37.33s of total 240.21s (15.5%). SpecDec 3078630: generation 33.71s, but total 241.13s. Generation-time speedup is 1.108x, but E2E step-time speedup is only 0.996x.
Why 58.88% acceptance can still be slower The 58.88% row is 30B reduced alltoall p8/g8 job 3076041, not a 235B 500K result. At that small/reduced shape, drafter/scheduler/cache overhead outweighed the saved target decode work. Acceptance alone is insufficient; the drafter must save more target-model work than the overhead it introduces.
235B expectation 235B in-house 500K drafter is still in hidden-state extraction and has not produced a clean 500K-trained NeMo-RL E2E result yet. HybridEP should be tested with 235B once the drafter is trained, but it should be reported as E2E acceleration, not Generation-throughput improvement.

Are we using vLLM native disable_by_batch_size? No. The NeMo-RL scripts intentionally reject SPECDEC_DISABLE_BY_BATCH_SIZE because that knob is request-admission scoped in some vLLM releases and can miss the active long-tail phase.
What gate is implemented? A runtime patch in nemo_rl/models/generation/vllm/vllm_worker.py patches both vLLM scheduler lookahead and GPU model-runner draft proposal. SpecDec draft work is skipped when active requests exceed VLLM_SPECDEC_BATCH_SIZE_GATE_THRESHOLD or scheduled tokens exceed VLLM_SPECDEC_BATCH_TOKEN_GATE_THRESHOLD. Adaptive mode adds NRL_SPECDEC_SCHEDULER_ADAPTIVE_GATE_PATCH_V1 and NRL_SPECDEC_ADAPTIVE_GATE_PATCH_V1, so scheduler and runner thresholds adjust toward a target enabled ratio. Dynamic-depth mode adds NRL_SPECDEC_SCHEDULER_DYNAMIC_DRAFT_CAP_PATCH_V1 plus NRL_SPECDEC_SCHEDULER_DYNAMIC_UPDATE_DRAFT_CAP_PATCH_V1, so the selected K caps both scheduler lookahead and the draft tokens stored back into scheduler request state.
Why this direction? The TLT adaptive drafter paper frames speculative decoding as most useful during long-tail rollout when the effective batch is small, and notes that fluctuating batch sizes can make always-on SD suboptimal. ReSpec makes the same system point for RL: static SD settings lose value at large batch sizes, so the server should choose SD settings from runtime workload signals. Our current gate is a practical approximation: keep SD off or shallow during large active batches and use deeper drafting only as request/token pressure falls.
How is this different from TLT? TLT does not rely on an unready learned drafter from the first token. It uses warm-up data and can fall back to model-free drafting early, while a spot trainer updates the learned drafter from target-model hidden states/tokens during rollout bubbles. ReSpec also adds online drafter evolution with reward-weighted KD. Current NeMo-RL runs use a fixed offline Speculators Eagle3 drafter plus adaptive request/token thresholds, dynamic K caps, and a new optional step-level acceptance controller that can lower K after weak acceptance. This tests adaptive serving first, but it does not yet implement online drafter refresh, reward-weighted KD, idle-GPU spot training, or model-free early rollout fallback.
