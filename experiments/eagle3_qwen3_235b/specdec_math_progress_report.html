Long-Tail Gate Status

QuestionCurrent Answer
Are we using vLLM native disable_by_batch_size? No. The NeMo-RL scripts intentionally reject SPECDEC_DISABLE_BY_BATCH_SIZE because that knob is request-admission scoped in some vLLM releases and can miss the active long-tail phase.
What gate is implemented? A runtime patch in nemo_rl/models/generation/vllm/vllm_worker.py patches both vLLM scheduler lookahead and GPU model-runner draft proposal. SpecDec draft work is skipped when active requests exceed VLLM_SPECDEC_BATCH_SIZE_GATE_THRESHOLD or scheduled tokens exceed VLLM_SPECDEC_BATCH_TOKEN_GATE_THRESHOLD.
Why this direction? The TLT adaptive drafter paper frames speculative decoding as most useful during long-tail rollout when the effective batch is small, and notes that fluctuating batch sizes can make always-on SD suboptimal. Our current gate is a practical approximation: keep SD off during large active batches and turn it on only as request/token pressure falls.
How is it enabled? Submission scripts pass ENABLE_RUNTIME_SPECDEC_GATE_PATCH=true, then map SPECDEC_SCHEDULER_PATCH_GATE_THRESHOLD and SPECDEC_SCHEDULER_PATCH_GATE_TOKEN_THRESHOLD into the vLLM worker env vars.
Is it present in the active 235B job? Yes. Job 3055926 logs show VLLM_ENABLE_RUNTIME_SPECDEC_BATCH_GATE_PATCH, VLLM_SPECDEC_BATCH_SIZE_GATE_THRESHOLD, and VLLM_SPECDEC_BATCH_TOKEN_GATE_THRESHOLD copied to vLLM workers. Values are redacted in Ray logs; the job tag records the token-gate setting as tokengate4096.
Is the patch bundle current? Yes. The source overlay validation now passes against the current markers: NRL_SPECDEC_BATCH_GATE_PATCH_V3, NRL_SPECDEC_SCHEDULER_LOOKAHEAD_GATE_PATCH_V5, request gate, and scheduled-token gate. The active remote nemo-rl checkout also contains those markers.

QuestionCurrent Answer
What is the current drafter training data? For the clean 30B path, the training pool is mixed non-OpenMath math: NuminaMath-1.5, NuminaMath-CoT, OpenThoughts-114k, math-deepscaler, and DAPO-Math-17k. Target responses are synthesized with Qwen/Qwen3-30B-A3B, then converted to Speculators Eagle3 training data.
What is the actual NeMo-RL test set? NeMo-RL rollout throughput and acceptance tests use openmath_reasoning_cot_conversations_50k.jsonl. It contains 50000 rows and 44304 unique normalized prompts. This file is the evaluation/test prompt source for the baseline and SpecDec NeMo-RL runs.
Does the mixed 500K training set overlap the NeMo-RL test set? No exact prompt-level overlap in the current exact-unique build. The OpenMath NeMo-RL evaluation prompts are loaded as a denylist before writing training rows. The denylist size is 44304, and the final merge/validation path reports records_written=500000, duplicate_prompts=0, and denylisted_prompts=0 for the final training file.
Which result has an OpenMath caveat? The older 30B OpenMath-trained SpecDec result, 1.17x-1.22x, is useful as an integration proof, but it is not the leakage-clean final claim. The clean comparison is mixed non-OpenMath training evaluated on OpenMath NeMo-RL prompts.
What is not mixed into the 500K clean set? The OpenMath NeMo-RL evaluation file is not used as a training source. Public HF Eagle3 checkpoints are also separate evaluation inputs, not part of this Speculators 500K training corpus.
What is the unit of uniqueness? User prompts are normalized by lowercasing and collapsing whitespace, then used as the uniqueness and denylist key. Assistant responses are target-model generations and are not used to decide train/test overlap.
