Long-Tail Gate Status

QuestionCurrent Answer
Are we using vLLM native disable_by_batch_size? No. The NeMo-RL scripts intentionally reject SPECDEC_DISABLE_BY_BATCH_SIZE because that knob is request-admission scoped in some vLLM releases and can miss the active long-tail phase.
What gate is implemented? A runtime patch in nemo_rl/models/generation/vllm/vllm_worker.py patches both vLLM scheduler lookahead and GPU model-runner draft proposal. SpecDec draft work is skipped when active requests exceed VLLM_SPECDEC_BATCH_SIZE_GATE_THRESHOLD or scheduled tokens exceed VLLM_SPECDEC_BATCH_TOKEN_GATE_THRESHOLD.
Why this direction? The TLT adaptive drafter paper frames speculative decoding as most useful during long-tail rollout when the effective batch is small, and notes that fluctuating batch sizes can make always-on SD suboptimal. Our current gate is a practical approximation: keep SD off during large active batches and turn it on only as request/token pressure falls.
How is this different from TLT? Current NeMo-RL runs use a fixed offline Speculators Eagle3 drafter plus static request/token thresholds. This avoids per-step draft proposal work when the local vLLM scheduled batch is large, but it still pays startup/model-load/CUDA-graph capture overhead and does not yet include TLT-style online drafter refresh, idle-GPU spot training, or automatic strategy tuning. The batch-gate jobs are therefore testing the scheduler idea first, not the full TLT system.
What did the gate code review find? The runtime patch is applied in both needed places: scheduler lookahead and GPU model-runner draft proposal. The remaining inefficiency is architectural: it is still one SpecDec-enabled vLLM engine with a static gate, so large-batch phases avoid proposal work but still carry drafter memory and SpecDec path overhead. The gate uses the scheduled request/token set, not simply the vLLM log line's total Running request count. Low-risk next code improvements are gate-hit counters, a shared gate predicate to avoid scheduler/model-runner drift, and then a two-engine bulk/tail rollout path if the hybrid threshold does not recover speed.
How is it enabled? Submission scripts pass ENABLE_RUNTIME_SPECDEC_GATE_PATCH=true, then map SPECDEC_SCHEDULER_PATCH_GATE_THRESHOLD and SPECDEC_SCHEDULER_PATCH_GATE_TOKEN_THRESHOLD into the vLLM worker env vars.
What was fixed in the submission scripts? Remote SpecDec-RL/Qwen30BA3B_GB200_Main_SpecDec.sh and SpecDec-RL/Qwen235B_GB200_Main_SpecDec.sh are on the guarded versions. They reject SPECDEC_DISABLE_BY_BATCH_SIZE, require ENABLE_RUNTIME_SPECDEC_GATE_PATCH=true when scheduler thresholds are set, keep CUDA graphs via enforce_eager=false, set async_engine=false, and expose NRL_VLLM_OMIT_GENERATION_LOGPROBS.
